What Hospital-at-Home eligibility is

Hospital-at-Home (HaH) delivers acute, inpatient-level care in a patient's residence: daily clinician visits, IV therapy, diagnostics, and continuous monitoring for a condition that would otherwise require a hospital bed.

This library is provided as a teaching and demonstration artifact. It has not been clinically validated, and the criteria it encodes are a published research protocol, not any particular organization's admission policy.

The clinical question is a screening one: of the patients presenting for acute admission, which can be safely treated at home instead? That question decomposes into inclusion and exclusion criteria. In clinical practice, all criteria are manually checked by clinicians, requiring full time screening staff to spend ~5–10 minutes per patient chart.

This library encodes the criteria described by Leff et al. (1997) in an original publication (https://doi.org/10.1111/j.1532-5415.1997.tb05968.x) and can be executed in <1s using CQL. Results are structured to support clinicians' eligibility decisions on criteria-level.

How the library is structured
Four layers

The library is organized into layers so that expensive operations happen once per patient rather than once per encounter per criterion.

Layer 0 — Base populations. One retrieve per resource type, with encounter-independent status filters applied exactly once (Qualifying Conditions, Final Observations, Qualifying Procedures, Qualifying Medication Administrations, and so on).

Layer 1 — Fluent filter functions. Reusable filters that operate on already-retrieved in-memory lists: codedAs, withCode, procedureCodedAs, linkedTo, during, performedDuring, administeredDuring, knownAsOf, onsetOrRecordedInKnownBy. No retrieves happen here.

Layer 2 — Coded subsets. Terminology matching runs once per patient per value set (or LOINC code) and is cached by the engine — Qualifying CHF Conditions, Systolic BP Results, Dialysis Performed, etc.

Layer 3 — Leaf criteria. One function per leaf criterion. Inclusion criteria use PresenceOf; exclusions use AbsenceOf with No … polarity (value true means the exclusion does not fire / the patient passes). Narrative criteria that cannot be decided from coded FHIR data return ManualReview() (value null, status Requires manual review).

Every leaf criterion returns a CriterionResult with three fields:

Field Meaning
value Boolean result; null when not computable from coded data
status Reason string when value is null; otherwise null
evidence FHIR resources the value was derived from

Layer 4 — Output. A single expression, Encounter Eligibility Results, returning one flat tuple per qualifying encounter. Each leaf unpacks into three elements ("…", "… [status]", "… [evidence]"); composites contribute a Boolean only. The row holds no nested tuples so the result is serializable to FHIR Parameters.

Criterion sections
Section Scope Roll-up
1 Inclusion — admission required, target diagnosis (CHF / COAD / CAP), age ≥ 65, catchment area 1. Inclusion Criteria Met
2 CHF-specific exclusions (evaluated only when CHF diagnosis is present) 2. No CHF Specific Exclusions Met
3 COAD-specific exclusions (evaluated only when COAD diagnosis is present) 3. No COAD Specific Exclusions Met
4 CAP-specific exclusions (evaluated only when CAP + infiltrate is present) 4. No CAP Specific Exclusions Met
5 General exclusions — applied to every patient 5. No General Exclusions Met

Condition-specific roll-ups are null when that diagnosis is not present; the final determination 0. HaH Eligible coalesces those to true so only the relevant branches constrain eligibility.

Some criteria split a coded leaf from a narrative stub (for example 5.1.1 / 5.1.2 for ICU acuity, or 4.2.1 / 4.2.2 for CXR abnormality). Composites Coalesce a null manual-review value to true so narrative gaps do not silently fail the patient.

Parameters
Parameter Default Purpose
IndexEncounterStatuses 'in-progress', 'finished' Which encounter statuses qualify
IndexEncounterClasses ACUTE, IMP, SS, EMER Which encounter classes count as inpatient
MinimumIndexEncounterLengthHours 24 Minimum stay to be considered an index encounter
MaxEncountersToEvaluate 10 Caps output size for patients with long histories
AllowedConditionClinicalStatuses active, recurrence, relapse, resolved Which conditions are in scope

Changing MinimumIndexEncounterLengthHours is the quickest way to see the encounter-selection logic respond.

Using the library
Working through it
  1. Start at the bottom. Read Encounter Eligibility Results (Layer 4) first. It is the whole protocol on one screen.
  2. Pick one criterion and trace it upward. 5.7. No General Exclusion Hypotension is a good first choice — it goes from a LOINC code through a Layer 2 subset, a Layer 1 during filter, and a quantity comparison, then wraps the evidence in AbsenceOf.
  3. Run the test bundles. Import the package, load a patient from the table below, and execute the library in Patient context.

When running Execute in CQL Studio, select only Encounter Eligibility Results as the result parameter. That expression is the library's intended output; leaving other definitions selected produces a large, unfocused result set of intermediate populations and helpers.

Terminology

The value set references point at VSAC canonical URLs (http://cts.nlm.nih.gov/fhir/ValueSet/...). The package includes the VSAC FHIR ValueSet resources required by the library. Intensional is-a (and other filter) definitions, plus grouping ValueSets that include them, are pre-expanded via VSAC into enumerated codes and an expansion snapshot so you do not need to import ICD, SNOMED, or other full CodeSystems to run this example. VSAC/UMLS license terms still apply to redistributed expansions.

If you swap in your own value sets, the declarations at the top of the CQL are the only thing you need to change.
