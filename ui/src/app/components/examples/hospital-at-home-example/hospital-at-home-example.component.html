What Hospital-at-Home eligibility is

Hospital-at-Home (HaH) delivers acute, inpatient-level care in a patient's residence: daily clinician visits, IV therapy, diagnostics, and continuous monitoring for a condition that would otherwise require a hospital bed.

This library is provided as ateaching and demonstration artifact. It has not been clinically validated, and the criteria it encodes are a published research protocol, not any particular organization's admission policy.

The clinical question is a screening one: of the patients presenting for acute admission, which can be safely treated at home instead? That question decomposes into inclusion and exclusion criteria. In clinical practice, all criteria are manually checked by clinicians, requiring full time screening staff to spend ~5–10 minutes per patient chart.

This library encodes the criteria described by Leff et al. (1997) in an original publication (https://doi.org/10.1111/j.1532-5415.1997.tb05968.x) and can be executed in <1s using CQL. Results are structured to support clinicians' eligibility decisions on criteria-level.

How the library is structured
Four layers

The library is organized into layers so that expensive operations happen once per patient rather than once per encounter per criterion.

Layer 0 — Base populations. One retrieve per resource type, with encounter-independent status filters applied exactly once (Qualifying Conditions, Final Observations, Qualifying Procedures, and so on).

Layer 1 — Fluent filter functions. Reusable filters that operate on already-retrieved in-memory lists: codedAs, withCode, linkedTo, during, performedDuring, knownAsOf. No retrieves happen here.

Layer 2 — Coded subsets. Terminology matching runs once per patient per value set and is cached by the engine — Qualifying CHF Conditions, Systolic BP Results, Dialysis Performed, etc.

Layer 3 — Enumerated criteria. One definition per criterion, named by its identifier in the source protocol (1.A.2. CHF Diagnosis, 5.G. General Exclusion Hypotension). Each is tagged in a comment with how it is evaluated:

Tag Meaning
[per-encounter] Filters a cached list against the index encounter
[lookback] Date window anchored to the encounter start
[patient-level] Cohort-wide, bounded by a retrospective cutoff
[manual-review stub] Constant; requires human adjudication
[inline] Computed directly in the Layer 4 output query

Layer 4 — Output. A single expression, Encounter Eligibility Results, returning one tuple per qualifying encounter.

Criterion sections
Section Scope
1 Inclusion — admission required, target diagnosis, age ≥ 65, catchment area
2 CHF-specific exclusions
3 COAD-specific exclusions
4 CAP-specific exclusions
5 General exclusions — applied to every patient

Each section rolls up into a Z.n summary, and those combine into the final determination Z.6. HaH Eligible.

Parameters
Parameter Default Purpose
IndexEncounterStatuses 'in-progress', 'finished' Which encounter statuses qualify
IndexEncounterClasses ACUTE, IMP, SS, EMER Which encounter classes count as inpatient
MinimumIndexEncounterLengthHours 24 Minimum stay to be considered an index encounter
MaxEncountersToEvaluate 10 Caps output size for patients with long histories
AllowedConditionClinicalStatuses active, recurrence, relapse, resolved Which conditions are in scope

Changing MinimumIndexEncounterLengthHours is the quickest way to see the encounter-selection logic respond.

Using the library
Working through it
  1. Start at the bottom. Read Encounter Eligibility Results (Layer 4) first. It is the whole protocol on one screen.
  2. Pick one criterion and trace it upward. 5.G. General Exclusion Hypotension is a good first choice — it goes from a LOINC code through a Layer 2 subset, a Layer 1 during filter, and a quantity comparison, in four short hops.
  3. Run the test bundles. Use a CQL engine to execute the library against patient test cases and check the results against the table below.
Test data

Four patient bundles are included in the package:

Bundle Expected Z.6. HaH Eligible Demonstrates
Bundle-Eligible true Inclusion met, no exclusions
Bundle-NotEligibleNoInclusion false Fails Section 1
Bundle-NotEligibleCHFExclusion false Fails Section 2 (conditional branch)
Bundle-NotEligibleGeneralExclusion false Fails Section 5

Load a bundle, then evaluate Encounter Eligibility Results in Patient context.

Terminology

The value set references point at VSAC canonical URLs (http://cts.nlm.nih.gov/fhir/ValueSet/...). The package includes the VSAC FHIR ValueSet resources required by the library. Intensional is-a (and other filter) definitions, plus grouping ValueSets that include them, are pre-expanded via VSAC into enumerated codes and an expansion snapshot so you do not need to import ICD, SNOMED, or other full CodeSystems to run this example. VSAC/UMLS license terms still apply to redistributed expansions.

If you swap in your own value sets, the declarations at the top of the CQL are the only thing you need to change.
